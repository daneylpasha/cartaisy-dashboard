# Dashboard Onboarding Flow

## Current state:

- Dashboard signup is invitation-only.
- Master-admin access to onboarding token management is implemented in `app/dashboard/admin/onboarding/page.tsx` using a hard-coded master admin email list.
- Onboarding tokens are stored in `models/OnboardingToken.ts` with `pending`, `used`, `expired`, and `revoked` statuses.
- `app/api/admin/onboarding-tokens/route.ts` can list, create, expire, and revoke onboarding tokens for master admins.
- `app/api/admin/send-onboarding-email/route.ts` can send onboarding emails through `sendOnboardingEmail`.
- `/signup?token=...` validates token status through `app/api/auth/validate-token/route.ts`, pre-fills email/store name when available, then submits to `app/api/auth/signup/route.ts`.
- Invite signup and `/login` share `app/(auth)/layout.tsx`, a centered card on the neutral `#f5f5f6` surface used by the setup wizard. When the token includes a store name or email, those fields stay locked and keep the invitation helper copy. Password checks and submit behavior are unchanged.
- When `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set, a valid invite shows Continue with Google as the first action and the password form under an "or" divider. Login shows the same button above the email form. The Google account email must match the invite and have `email_verified`. Signup then calls backend `POST /auth/google` with that ID token and sends the merchant to `/dashboard/onboarding`. The button is omitted when the client id is unset.
- Signup creates a `Store`, creates the first `User` as `super_admin`, marks the token as used, and on a successful sign-in redirects to `/dashboard/onboarding`.
- Login still opens `/dashboard` from the auth page. A successful password reset does the same from `/reset-password`. Middleware (`lib/dashboard/entry.ts`) continues that visit to `/dashboard/onboarding` when `GET /api/v1/shopify/status`, parsed like the wizard, says the store is not connected. The reset page counts as that auth entry by referrer. `/forgot-password` does not. A connected store stays on Home and sees one Go live strip. A ready public https install URL is a compact code on the preview step, which opens Build for the larger code. While the newest request is queued or building and that URL is missing, the preview step says the preview is building. Scan wins when a ready public URL exists. Shopify reconnect and billing stay one safety notice in the strip lead, with the reconnect action and without a second copy. The header count is the checklist rows and how many are done. The strip does not replace the disconnected checklist. A status check that fails does not redirect. The redirect does not apply to other dashboard URLs, and Exit setup does not bounce back into the wizard. Home for a disconnected store is a checklist that links to the wizard steps; it does not replace the wizard. Add app in the shell sidebar creates a blank store with `POST /api/v1/auth/stores` and opens this wizard for that new active store. An owner with another app can remove this one from Switch app after typing its name. The last app stays, so the only store cannot be deleted until another app exists. Switching to an existing app opens `/dashboard` and does not start the wizard. The previous app's branding cache is cleared first. Exit setup still returns to Home for the store that is active then.
- The guided wizard at `app/dashboard/onboarding/page.tsx` is the post-signup path: Connect Shopify, confirm brand, preview a starting home, then a ready-for-build step. It does not replace invite signup and it does not require the home module editor. The wizard shell comes from dashboard #16 / PR #18. This change does not restyle it.
- The first-party cookie banner is not shown on `/dashboard/onboarding` or nested wizard paths, so it does not cover the Brand card. That hide does not record consent. Leaving the wizard shows the banner again until the merchant chooses. Cookie Settings remains on the marketing footer and on `/cookies`.
- Connect stays in `lib/onboarding/shopifyConnect.ts` and calls backend Shopify routes only. `liveRedirectEnabled` is true. Connect Shopify opens the authorize URL from `POST /api/v1/shopify/oauth/connect`. Under the store field, the step explains that the address must end in `.myshopify.com` (a custom domain or a public storefront link will not connect), where to find that domain in Shopify admin, and that a pasted `https://` link is trimmed to the domain. Settings → Shopify Connection shows the same guidance. `normalizeShopDomainInput` and `normalizeShopInput` are unchanged, and Continue without connecting is unchanged. The merged backend ignores a client `returnTo` and sends the browser to `SHOPIFY_OAUTH_RETURN_URL`, adding `shopify=connected` or `shopify=error` plus `reason` and `shop`. The connect step reads that query, shows `shopifyReturnCopy`, then removes `shopify`, `reason`, `shop`, and a legacy `error` param so a refresh does not repeat the banner. A connected return shows sync progress from `GET /api/v1/shopify/sync`, the product count from the overview snapshot, and the last sync time when the durable status has one. When that status is idle or failed, the step calls `POST /api/v1/shopify/sync` once. A 409 in-progress response does not start another sync; the step polls GET until the run finishes and the Sync again control stays busy. A failed sync shows `errorSummary` when that text is safe. `webhookRegistrationError` from connection status is shown when present. If the catalog is already eligible and that webhook error is set, the one control is Reconnect Shopify. Otherwise a connected store that is not eligible gets Sync again, and a healthy catalog gets Sync again only as a quiet action. Shop id is not shown. A return of `shopify=error` uses Reconnect Shopify. Continue to Brand stays available during sync. This wizard does not write `shopify.accessToken` in dashboard Mongo. A sync, overview, or collections response with `shopify_reconnect_required` shows Reconnect Shopify. `shopify_payment_required`, `shopify_store_billing_required`, HTTP 402, or a "Payment Required" summary shows that the Shopify plan needs attention, does not auto-start Sync again, and does not offer Sync again as the fix.
- Branding reuses `GET`/`PATCH /admin/stores/:storeId/branding` and `POST .../branding/logo` for colors and logo. App name is saved with `PATCH /api/store` `{ name }`. A name that is only Cartaisy after trim is rejected before that request, and the field says to choose the name shoppers see on the app. The same PATCH returns 400 if that name is posted. Settings store name uses the same rule. A merchant name of at least 2 characters that is not only that wordmark still saves. Splash and icon upload as soon as the merchant picks a file, the same way the logo does. Before that request, the brand step and Settings → Store Branding read the image size. Logo, app icon, and splash each show the recommended Android and iOS size. A file that is the wrong type, over 2MB, or outside the allowed pixels is rejected with a reason, the previous image stays, and nothing is uploaded. Use logo checks the fetched file against the icon or splash rules, so a square logo can still become the splash. The form shows the local preview immediately, then the saved https URL. Upload tries `POST .../branding/splash` and `.../branding/icon` first. A successful response already stores the https URL on branding, and the wizard keeps that URL. It does not also require `brandAssets`. Signed upload runs only when that POST returns 404, 405, or 501. That path uploads only when the signature says `canUpload`, then calls `POST /notifications/stores/:storeId/images/register` before the URL is kept. `PATCH /api/store` stores `{ brandAssets: { iconUrl, splashUrl } }` only for that fallback. Reload reads branding `iconUrl` / `appIconUrl` and `splashUrl` / `splashImageUrl` when the payload includes them, for the brand form and the Build my app icon, and otherwise uses that store record. The brand step does not show a phone. Name, colors, logo, icon, and splash stay on the form and save as before. If the logo is a drawable https or blob image and the app icon is missing, unsafe, or broken, Use logo fetches that file and saves it with the existing icon upload. A failed fetch leaves the icon empty. The Splash field offers the same control when that logo is drawable and the splash is missing, unsafe, or broken. That click saves the file with the existing splash upload and does not copy the logo URL onto the splash. A failed fetch leaves the splash empty. Continue stays on the existing rules. When no ready public https install URL exists, the column beside the form explains the first build: confirm brand, publish home, open Build my app, then scan the install code on the Home Go live strip. A ready install URL replaces that panel with the compact code. Clear on a color keeps the platform-default swatch locally. Continue sends JSON `null` for each cleared color on `PATCH /admin/stores/:storeId/branding`. A reload treats a null or missing color as the platform default and does not keep the previous hex as a saved color. Save and Continue otherwise stay as they were.
- Preview (`components/onboarding/steps/PreviewStep.tsx`) shows `BrandInstallPreview`, the same column as the brand step and Settings → Store Branding. When no ready public https install URL exists, including a failed build list, that column shows first-build instructions. While the list is loading, those instructions are not shown over an install already on screen. A ready public https install URL centers a compact code and Open Build. None of those screens show a shopper phone. The wizard header shows the app display name when branding or the store name is known, and otherwise Setup, with a small rounded icon when the branding draft has a safe https or blob app icon (the logo only when that icon is missing). A broken or unsafe image is hidden and the text mark stays. It does not use Cartaisy, a shop domain, or a store id. `/dashboard/app-builder/preview` is a module stack, not a shopper phone. Catalog counts come from `GET /shopify/overview`. Collection names come from `GET /shopify/collections`. The snapshot does not request preview product tiles.
- The ready step is the Build my app screen. It calls `POST /api/v1/build-requests` with Android and iOS booleans and an optional access note, then polls `GET /api/v1/build-requests/:id` until each requested platform is ready or failed. Those calls use the shared dashboard client, which refreshes an expired access token and retries once. Submit stays disabled unless `GET /api/v1/shopify/sync` says `eligibleForBuild` and Shopify is connected. Above Platforms, a soft strip shows the app display name, icon, and splash. A non-empty trimmed merchant name from the branding draft is shown as itself. A name that is only Cartaisy after trim is treated as missing. A missing, blank, whitespace-only, or Cartaisy-only name uses calm copy and links to the Brand step and Settings Store Branding. The strip does not invent a name and does not fall back to Cartaisy, the shop domain, or a store id. Icon and splash thumbs appear when those branding URLs are public https, with the same calm missing state when one is absent. Token-shaped and non-https URLs are not shown. A missing name, icon, or splash does not disable submit. As of 2026-09-29, when `GET /api/home-layout` is Not published yet or Draft, a quiet strip under the name, icon, and splash strip shows that status and links to `/dashboard/app-builder#publish-home`. Published, and a failed or unrecognized read, leave the strip off. The strip does not disable Build, install codes, or Submit. A disconnected store sees Reconnect Shopify and a plain reason. A connected store that is not eligible sees Sync again. `shopify.lastSyncAt` does not enable it. Try again reloads the wizard's Shopify connection snapshot together with catalog sync and the build list, so a failed status check does not stay stuck until a full page reload. When a platform is ready and the backend sent a non-empty https `installUrl`, the screen shows Install Android build or Install iOS build and opens that URL in a new tab. A ready platform without that URL keeps the Ready label, says the install link will show here when it is available, and does not show a button. The screen does not invent a URL. As of 2026-09-29, a ready public https install URL is also a large code above the platform cards, with the URL as text and Copy link. The code is drawn in the browser from that URL only. Building, missing, and unsafe URLs do not get a code. Queued, building, and ready without that URL keep a calm note in that row: a scannable install code will appear when the preview is ready. The progress cards stay. While a requested platform is queued, building, or waiting, the page shows a progress card and updates on its own, including a refresh when the tab becomes visible again. Queued, building, and ready share a three-step rail. A failed platform says the build did not finish and does not name the build tooling. A request that stays queued keeps polling. Cartaisy operators update those statuses, and can paste or clear an Expo install link, from `/dashboard/admin/build-requests`. That page is not part of the merchant wizard. A store owner, including `super_admin`, cannot open the queue. The same step, under Build my app, connects the store's App Store Connect API key and Google Play service account. Settings → Build setup shows the same connection. The upload goes to `POST /api/v1/store-credentials/apple` or `.../google` and is not shown again. Status is connected, missing, or needs attention. Disconnect removes one platform. A missing or needs-attention credential does not disable preview, Build my app, or an install link. When a requested platform is ready and that platform's account is connected, the platform card shows Submit to App Store or Submit to Play. The button calls `POST /api/v1/build-requests/:id/submits` and the page keeps polling that platform while the submit is queued or submitting. A build that is not ready disables only that button and says why. A ready platform with a missing or needs-attention account shows Connect Apple Developer or Connect Google Play, which opens the store-account card already on this page. Install links stay on the same card. After the store accepts the upload, the card confirms what was sent, where to check the review (App Store Connect or Play Console), and a plain review-time note. It does not add a store URL. A failed submit shows the safe message and can be started again. Queued and submitting stay a quiet status. Settings → Build setup shows the same control for the latest build. The screen does not show private keys, service-account JSON, or Expo tokens.- Store setup can still continue through dashboard settings. Settings → Store Branding can replace the app icon and splash with the same upload contract as the brand step, and does not show them on a phone. The same first-build steps, or the install code when one is ready, sit beside the form. That Shopify card also uses the backend and does not persist an access token. One control is shown: Sync again when connected but the catalog is not build-eligible, Reconnect Shopify when disconnected or when webhook registration failed after a successful sync. The older admin sync-status card is not on this page.

## Target state:

- MVP onboarding should guide merchants through:
  1. Receive invite/onboarding link.
  2. Validate link and create owner account.
  3. Create or confirm store identity.
  4. Connect Shopify.
  5. Confirm store setup/status readiness.
  6. Configure branding/theme fields required by mobile.
  7. Configure home modules and Shopify collection/product references.
  8. Preview the mobile home screen.
  9. Enter build/release handoff when that workflow exists.
- Required merchant information should include owner email, store name, Shopify shop domain, branding assets, currency/timezone from Shopify, and module content/references.
- Admin visibility should show whether a merchant is ready for MVP release, not just whether they can log in.

## Known gaps:

- Do not assume any feature or behavior described above is implemented unless verified in the current code.
- The wizard is a guided setup path, not a canonical persisted readiness record. Leaving and returning does not remember an "onboarding complete" flag. Routing treats "Shopify connected" as the established-store signal for that reason. Preview is not marked complete on Home, because nothing stores it.
- Live Shopify connect from the wizard is on. After `shopify=connected`, the connect step shows success, catalog sync, and the product count (or "Not synced yet"). The merchant can continue to branding while sync is still running; the brand step keeps the sync warning. Build stays off until `GET /api/v1/shopify/sync` reports a succeeded catalog sync and Shopify is connected, including when that status cannot be read. The browser returns to the wizard only when backend `SHOPIFY_OAUTH_RETURN_URL` points at `/dashboard/onboarding?step=connect`.
- Branding GET and the icon/splash upload responses are the icon and splash source when those fields are present. Dashboard `brandAssets` remains the store record for the signed fallback, used only when `POST /branding/icon` or `POST /branding/splash` returns 404, 405, or 501. That fallback checks `canUpload` and registers the file with `POST /notifications/stores/:storeId/images/register`, the same store image record the notification uploader uses. The https URL is kept only after registration succeeds. A store at its image limit is not uploaded. There is still no icon or splash delete route, matching logo replacement.
- Token master-admin authorization is implemented with hard-coded real email identifiers in audited files; this is both an operational ownership concern and a security/PII concern because source-embedded identifiers persist in git history and may appear in client bundle analysis. Future work should move this allowlist to a server-side environment variable or database-backed admin record instead of expanding the in-source list.
- Historical access tokens that were written by the old dashboard callback are not migrated. A store that was connected only in that database shows as disconnected until the merchant connects again.
- Branding/theme setup beyond logo, timezone, and currency was not verified.
- Product picker was not identified.
- Preview exists. The ready step requests a tracked build and shows live status. Store Apple and Google credentials can be saved from that step and from Settings. A finished build can be submitted to the App Store or Google Play from Build my app and from Settings → Build setup when that platform's account is connected. Release publishing beyond that submit, and rollback automation, are still not implemented.
- Email delivery depends on provider configuration. `.env.example` documents the Google client id only, not the email provider.
