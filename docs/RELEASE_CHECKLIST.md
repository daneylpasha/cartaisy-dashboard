# Dashboard Release Checklist

## Current state:

- Dashboard release readiness was not previously documented in a repo-level checklist.
- Verified commands include `npm run lint`, `npm run type-check`, `npm run build`, `npm run dev`, `npm run start`, `npm run test:api`, and `npm run generate:api`.
- CI exists as of 2026-07-28: `.github/workflows/ci.yml` runs `npm ci`, `npm run lint`, `npm run type-check`, `npm run test:auth-google`, and `npm run test:auth-password-reset` on every pull request against `main`, on Node 20, with actions pinned by commit SHA. The Google check covers the invite signup decision. The password-reset check covers token shape and public copy. There is still no general automated test suite.
- No environment example file was found during the audit.
- The dashboard currently includes settings, Shopify connection, store branding/logo upload, app-builder modules, homescreen preview, admin onboarding token pages, and a post-signup setup wizard at `/dashboard/onboarding`. The wizard ready step submits a tracked build request when the catalog sync succeeded and Shopify is connected.

## Target state:

Before release, verify:

- Pre-release checks: dependencies installed, `npm run lint` and `npm run type-check` pass (both are enforced on every PR by CI), build passes, relevant manual dashboard flows checked, and no unrelated files are included. The 176 pre-existing violations of three rules are recorded in `eslint-suppressions.json` and those rules stay at `error`, so the debt cannot grow: a violation in an unrecorded file, a count above the recorded one, or a fix in one file paired with a new violation in another all fail. See `eslint.config.mjs` for the one case that does not fail — swapping a violation for another within the same file for the same rule.
- Environment variables: backend API URL, auth/session URLs, MongoDB connection, email provider credentials, and any analytics settings are configured in deployment without exposing secret values in frontend code. Continue with Google needs `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (the Identity Services client id). Optional `GOOGLE_CLIENT_ID` overrides the audience used when invite signup verifies the ID token; otherwise the public client id is used. The Google client must allow the dashboard origin. When the public client id is unset, the button is hidden. `.env.example` documents these two names only. Partner app secrets (`SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`, `SHOPIFY_REDIRECT_URI`, `SHOPIFY_SCOPES`) stay on the backend. Set backend `SHOPIFY_OAUTH_RETURN_URL` to `https://<dashboard>/dashboard/onboarding?step=connect` so a new merchant returns to the wizard after Shopify authorizes. The backend ignores any `returnTo` sent by the dashboard. Settings still reads `shopify` and `reason` if that URL is pointed at settings instead. The dashboard connect flow does not read `SHOPIFY_API_KEY` or `SHOPIFY_API_SECRET`.
- Auth/session: login, token cookie handling, backend profile verification, protected dashboard redirects, signout, forgot password, and reset password. Forgot password should show the same success copy for any email. Reset should accept the email link, reject a missing or malformed token without showing it, and after a real reset land in the dashboard without the token or the new password in the URL. Continue with Google stays on the sign-in page.
- Store context: every dashboard route uses the authenticated store context and respects role permissions.
- Backend API compatibility: generated/direct backend calls match deployed backend endpoints and response shapes.
- Shopify: connect, status, reconnect, sync again, disconnect, and collections go through the backend. Confirm a new connect does not write `shopify.accessToken` on the dashboard store. The retired dashboard callback redirects to settings and does not exchange a code. A catalog response of `shopify_reconnect_required` shows Reconnect Shopify. `shopify_payment_required`, `shopify_store_billing_required`, or HTTP 402 shows that the Shopify plan needs attention and does not offer Sync again.
- Merchant onboarding: token creation, token expiry/revocation, email delivery if enabled, signup token validation, store creation, first-user role, post-signup login, and the `/dashboard/onboarding` steps. Connect Shopify opens the backend authorize URL. A return with `shopify=connected` shows success, sync progress, and the product count or "Not synced yet", and Continue to Brand stays available. A return with `shopify=error&reason=` shows plain copy and Reconnect Shopify. Refreshing does not repeat that banner. Branding save and the shopper-chrome preview (opening, default home, product, cart) still apply. Build my app stays disabled until `GET /api/v1/shopify/sync` reports `eligibleForBuild` and Shopify is connected. A missing app name, icon, or splash does not disable it. A Not published or Draft home shows a quiet strip with a link to Publish home and does not disable Build, install, or Submit. A published home, or a failed layout read, leaves that strip off. The soft strip shows a trimmed display name when the branding draft has one, and calm missing copy with links to Brand and Store Branding when the name is blank. That missing name is not replaced with Cartaisy, the shop domain, or a store id. Confirm the wizard did not write a Shopify access token.
- Branding/theme configuration: logo upload/remove, current branding fetch, and any mobile-consumed theme fields. On the brand step, an app icon and splash upload and still show in the form after reload. The brand step does not show a phone. A missing ready install shows first-build instructions. A ready install shows the code. Neither state blocks save or Continue. The screen must not ask for an API key or a Shopify access token.
- Home module publishing/editor checks: module create/edit/reorder/visibility, collection reference selection, homescreen preview, backend/mobile contract compatibility, and validation of store-owned Shopify references. On App Builder, a store with no saved sections and no saved draft shows Not published yet. A store that already has `sections` shows Published. Save draft does not replace `sections`. Unpublish, after a plain confirmation, sets `sections` to an empty list and clears `publishedAt`, keeps `draftSections`, and does not delete module documents. A non-empty draft then shows Draft and says the installed app uses the smart default until Publish again. Publish home says the installed app reads that section order under the home header. An edit after that publish must say Draft and must not say the edit is already live. A billing or reconnect failure in a collection picker shows the catalog block, not an empty select. The module-stack preview stays outside the shopper phone and does not add Cartaisy chrome inside the frame. Connected Home shows Not published yet, Published, or Draft from that same layout. Not published and Draft link to Publish home. A failed layout read does not show a status. The Brand and Preview phone caption says the installable app shows the published home or the smart default until Publish, and that module-stack edits stay off the device until then.
- Build/status workflow: onboarding preview shows first-build instructions when no ready install URL exists, and the install code when one does. It does not show the shopper phone. On the ready step, an ineligible store cannot submit and sees Reconnect Shopify or Sync again. Settings shows the same one control: Sync again when the catalog is connected but not eligible, Reconnect Shopify when the store is disconnected. The card shows the last sync time, the product count, or the short failure, including `webhookRegistrationError` when status includes it. It does not ask for an Admin API key. Try again also refreshes Shopify connection status. An expired access token on that screen refreshes and retries once. An eligible store can request Android, iOS, or both and sees per-platform status, including Waiting on Apple for iOS. While a platform is queued or building, the page shows a progress rail and updates on its own, including when the tab becomes visible again. A failed platform says the build did not finish and must not show a build log, an EAS id, or tooling names. A request that stays queued still accepts an ops install-link paste. When a platform is Ready and the backend sent a non-empty https `installUrl`, the merchant sees Install Android build or Install iOS build, which opens that URL in a new tab. Ready without that URL has no install button, and the screen must not invent one. A ready public https URL also shows a large install code above the platform cards, the URL as text, and Copy link. Building, missing, and unsafe URLs do not. Queued, building, and ready without a public URL show a short note that a scannable install code will appear when the preview is ready, in the same row as the code, and must not draw a stand-in code. The progress cards stay. On Brand, Preview, and Settings, the phone stays only until a ready install URL exists. While the build list is loading, the phone is not shown. After a ready install URL, those screens show a compact code and Open Build instead of the phone. Branding editors stay. A failed build list keeps the phone. On Home for a connected store, Go live is one strip. A ready public https install URL shows a compact code on the preview step and Open Build. That code is absent when no ready public URL exists. When the newest request is queued or building and no ready public URL exists, the preview step says the preview is building and offers Open Build. That state is absent when a ready public URL exists, when the newest request failed or is waiting, and the strip does not add a second action while Shopify needs reconnect or billing. That billing or reconnect story appears once, in the strip lead, with reconnect still available. The header count matches the checklist rows. On the ops queue, paste an https link on expo.dev or expo.io with the status update, confirm it shows on the row, and confirm Clear removes it. A non-Expo host must not be saved. A blank app name on that screen stays a calm missing state and does not disable the request. Store Apple and Google credentials on that screen and on Settings → Build setup also do not disable the request or the install link. When a platform is ready and that account is connected, Submit to App Store or Submit to Play is enabled and calls the backend submit route. A build that is not ready disables only that submit button. A ready platform with a missing or needs-attention account shows Connect Apple Developer or Connect Google Play and opens the existing account card on the same page. After a successful submit, the screen confirms the upload, names App Store Connect or Play Console, and gives a plain review-time note without a store URL. A failed submit shows the safe message and can be tried again. While a submit is queued or submitting, the status stays quiet. Home shows the same note when that build has a submit, with a link back to Build, and does not start a submit. Confirm the screen does not show a private key, a service-account JSON, or an Expo token. Also verify the existing app-builder homescreen preview. `/dashboard/admin/build-requests` is for platform operators only. A store owner must see the empty 403 state, not another store's access note. Grant ops on the backend (`isPlatformOperator` or `PLATFORM_OPS_EMAILS`) before expecting the queue to load. The dashboard has no setting for that allowlist. A row with branding shows the app icon and splash and copies only the public https assignment (`SPLASH_IMAGE_URL=…` for splash, `ICON_IMAGE_URL=…` for the icon when present). A non-empty app name copies as `APP_NAME=…` with no extra quotes. A valid 24-character hex store id copies as `EXPO_PUBLIC_STORE_ID=<id>` with no quotes, labeled `EXPO_PUBLIC_STORE_ID=…`, and the raw id is not the row title. A row without those image fields stays empty and must not show a token or a made-up image URL. A missing or blank app name shows a calm empty state and must not copy Cartaisy, the shop domain, or a store id. A missing or invalid store id shows a calm empty state and must not copy the build-request id, the shop domain, or the app name. When one or more of those assignments is copyable, `Copy all EAS env` pastes them as one block (`APP_NAME`, `ICON_IMAGE_URL`, `SPLASH_IMAGE_URL`, `EXPO_PUBLIC_STORE_ID`, present lines only, `KEY=value`, no quotes, LF newlines). If none qualify, that control is absent. The block matches Cartaisy `docs/MOBILE_MERCHANT_PROVISIONING_RUNBOOK.md`. The four single-field controls stay.- Rollback notes: identify the deployed version, environment variables changed, database migrations/manual scripts, and any generated API client changes before release.
## Known gaps:

- Do not assume any feature or behavior described above is implemented unless verified in the current code.
- Store Apple and Google credentials are stored by the backend from Build my app and Settings → Build setup. Confirm a save shows only the key id last 4, issuer id last 4, or Google client email, and that disconnect returns that platform to missing. A missing credential must not disable Build my app or an install link. Submit to App Store and Submit to Play are available when that platform is ready and its account is connected. A ready platform with a missing or needs-attention account shows Connect Apple Developer or Connect Google Play instead of a disabled submit button. A build that is not ready still disables only that submit control. Release publishing beyond that submit, and rollback automation, are still not implemented. The tracked build request plus this submit is the v1 handoff.
- CI covers lint and typecheck only. There is no unit, integration or e2e test runner, and no build step in CI, so a release still needs manual verification of the flows listed above.
- `.env.example` documents `NEXT_PUBLIC_GOOGLE_CLIENT_ID` and optional `GOOGLE_CLIENT_ID` only. It is not a full environment catalog. Deployments must still be checked without exposing secrets.
- Current Shopify and branding flows include direct dashboard/backend API calls that need security review before major release changes.
