# Dashboard Architecture

## Current state:

- Framework/runtime: Next.js App Router, React, TypeScript, Tailwind CSS, Mongoose/MongoDB, and client/server fetch helpers. `package.json` lists Next `^16.1.4`, React `19.2.0`, Mongoose `^9.0.0`, NextAuth as a dependency, and an Orval-generated API client setup.
- App structure: public marketing/docs pages live under `app/`; authenticated dashboard routes live under `app/dashboard`; local Next API routes live under `app/api`; reusable UI lives under `components`; hooks live under `hooks`; API helpers, services, and auth helpers live under `lib`; data models live under `models`.
- Dashboard frame: routes other than the setup wizard use `components/dashboard/DashboardShell.tsx`. The frame is `h-dvh` and `overflow-hidden`, the sidebar fills that height, and the main column scrolls. While it is mounted, `html` and `body` use the same `#f6f6f7` surface as the frame. Marketing pages keep `html` at `#0A0A0A`. The wizard keeps its own `min-h-screen` surface and does not use this frame.
- Auth/session: middleware protects `/dashboard` routes based on a `cartaisy_token` cookie. `lib/auth/server.ts` verifies the token by calling the backend `/auth/profile` endpoint. Client auth helpers store tokens/user data through `lib/api/mutator/custom-instance.ts`. After login, middleware may send the browser to `/dashboard/onboarding` instead of Home. That decision is in `lib/dashboard/entry.ts`. It runs for `/login`, `/signup`, the next exact `/dashboard` hit after those pages, and a `/dashboard` hit whose referrer is `/reset-password` after a successful password reset. `/forgot-password` and `/reset-password` are not auth routes in middleware, so an already signed-in merchant can still open a reset link. It calls `GET /api/v1/shopify/status` and uses `normalizeConnectionStatus`. A failed status check does not redirect. Deep links under `/dashboard/*` are not redirected. Exit setup (`/dashboard` with the onboarding page as the referrer) stays on Home, so the wizard does not loop. The entry cookie is `cartaisy_auth_entry` (httpOnly, short-lived, not a credential). `/login` and `/signup` share `app/(auth)/layout.tsx`: a centered card about 440px wide on the same neutral `#f5f5f6` surface as the setup wizard. That shell is presentation only. When `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set, both pages offer Continue with Google. Login posts `{ idToken }` to backend `POST /auth/google` and reuses the password-login session. Invite signup still goes through `app/api/auth/signup`; a `googleIdToken` is verified with `google-auth-library` (audience `GOOGLE_CLIENT_ID` or the public client id) and must match the invite email. Forgot password and reset password use the same centered card. `/forgot-password` posts `{ email }` to backend `POST /api/v1/auth/forgot-password` and always shows the generic success copy. `/reset-password` reads a 64-character hex `token` query, checks the new password locally (including a confirm field the API does not accept), and posts `{ token, newPassword }` to `POST /api/v1/auth/reset-password`. A success stores `data.token` and `data.refreshToken` with the same `tokenStorage.setTokens` path as login, then opens `/dashboard`. The reset token and the new password are not rendered, logged, or kept on the URL after submit.
- Store context: dashboard server routes generally read `session.user.storeId` and query/update store-scoped Mongoose models. Role helpers in `lib/utils/permissions.ts` distinguish `super_admin` and `admin` capabilities.
- API client flow: local dashboard routes use `fetch`, `getServerSession`, and Mongoose services. Shopify connect, status, disconnect, sync, and collection reads go to the backend through `NEXT_PUBLIC_API_URL` (`lib/api/shopifyConnection.ts`, `lib/onboarding/shopifyConnect.ts`, and the collections proxy). Generated/backend API calls use Orval with `lib/api/mutator/custom-instance.ts` and `NEXT_PUBLIC_API_URL`, defaulting to the production Railway backend URL. The dashboard does not exchange Shopify OAuth codes or store Admin access tokens for new connects.
- Cookie consent: `components/cookies/CookieBanner.tsx` is mounted from the root layout. On `/dashboard/onboarding` and nested wizard paths it is not rendered, so the sticky strip does not cover the phone or the Brand card. That path check does not write `cartaisy_cookie_consent`. Other routes still show the banner until a choice is stored. The marketing footer and `/cookies` keep a Cookie Settings control that opens the same banner.
- Merchant onboarding: `app/dashboard/admin/onboarding/page.tsx` lets hard-coded master admin emails manage onboarding tokens through `app/api/admin/onboarding-tokens/route.ts`; `/signup?token=...` validates the token through `app/api/auth/validate-token/route.ts`; signup creates a Store and first `super_admin` User through `app/api/auth/signup/route.ts`, then sends the new merchant to `/dashboard/onboarding`. Login still navigates to `/dashboard` from the auth page; middleware continues that visit into the wizard when Shopify is not connected. The wizard shell hides the dashboard sidebar. Its header shows the app display name when branding or the store name is known, and otherwise Setup. It does not use Cartaisy, a shop domain, or a store id. Exit setup stays a link to Home. Connect, branding, preview, and the ready-for-build step live under `components/onboarding/`. Shopify calls for that flow go through `lib/onboarding/shopifyConnect.ts` (backend only, no dashboard token write). Live redirect is on: Connect opens Shopify, and the merchant returns through backend `SHOPIFY_OAUTH_RETURN_URL`. The connect step then shows success or the reason-code error, strips that return query, and reads catalog sync plus the overview product count. A connected return may call `POST /api/v1/shopify/sync` once when status is idle or failed, and polls `GET /api/v1/shopify/sync` while status is syncing. The connect step shows one recovery control: Sync again while the catalog is connected but not build-eligible, or Reconnect Shopify when webhook registration failed after a successful sync. Brand stays available during that sync. Shop id is not shown on that step. A reconnect or Shopify billing code on sync, overview, or collections replaces that control with Reconnect Shopify or a billing notice that does not offer Sync again. Branding calls go through `lib/onboarding/branding.ts`. Home for a disconnected store is a checklist in `components/dashboard/home/` that links to those steps. It does not start connect or a build itself. A connected store's Home shows catalog sync, build status, and counts from those APIs. Connected Home shows one Go live strip for that path: Shopify, catalog sync (build eligibility), brand name and icon, home publish status from `GET /api/home-layout`, preview install, optional Apple and Google accounts, and the latest submit. The first required step that is not done is the only filled action. Not published and Draft link to App Builder `#publish-home`. A failed read degrades that step and does not invent done. A ready public https install URL draws a compact code inside the preview step and does not invent a URL. A queued or building newest request, with no ready public URL, is the preview step's building state. Scan wins when a ready public URL exists. The header count is those checklist rows and how many are done. Shopify reconnect and billing stay one safety notice in the strip lead, with the reconnect action and without a second copy.
- Branding/theme configuration: settings show store info, the Shopify connection card (catalog recovery lives on that card), plan/usage, app settings, a logo upload section, and a primary/secondary color editor. `StoreLogoUpload` and `components/settings/StoreBrandingColors.tsx` both call the same backend branding endpoints (`GET`/`PATCH /admin/stores/:storeId/branding`) using `NEXT_PUBLIC_API_URL`, each fetching its own copy of branding data independently on mount rather than sharing state — see Known gaps. `StoreBrandingColors` reuses the existing `components/ui/color-picker.tsx` primitive (also used by the promo/callout/carousel forms) for hex input and validation. Store timezone/currency are shown as Shopify-synced values. The brand step also uploads an app icon and a splash. Those files go to `POST /admin/stores/:storeId/branding/icon` and `.../splash`. A successful response is the saved icon or splash (`iconUrl` / `appIconUrl`, `splashUrl` / `splashImageUrl` on branding GET and PATCH). The signed store-image upload runs only when that POST returns 404, 405, or 501: `canUpload` must be true, and `POST /notifications/stores/:storeId/images/register` must succeed before the https URL is kept on store-scoped `GET`/`PATCH /api/store` `brandAssets`. That record is not a Shopify token. Reload prefers branding icon and splash URLs when the backend returns them, on the brand form, the live phone, and the Build my app icon. `brandAssets` fills only a field branding omitted. Settings → Store Branding (`components/settings/StoreAppBrand.tsx`) uses those same helpers and the same phone for icon and splash. A successful branding POST is not copied into `brandAssets`. The device screen has no Cartaisy chrome. Below that phone, the brand step and Settings Store Branding render `HomeScreenLauncherMock`: a public https icon or a blob draft, plus a non-empty trimmed display name. The icon reuses `displayBrandImageUrl` and then keeps only https and blob, so token-shaped and other non-https URLs are dropped. A missing icon or blank name stays a partial state with the Brand and Store Branding links. The mock does not gate save, Continue, or Build submit. They also render `SplashBootMock` under that mock: a public https splash or a blob draft as a full-bleed frame, with the trimmed display name captioned only when it is non-empty. The splash reuses `displayBrandImageUrl` and then keeps only https and blob. A missing splash stays a blank frame with the same Brand and Store Branding links. It does not use the logo or icon as a substitute and does not gate save, Continue, or Build submit.
- Onboarding preview catalog: after catalog sync succeeds, `loadShopifySnapshot` attaches up to four products for the preview phone. Counts still come from `GET /shopify/overview`. Tiles come from a product list on that overview payload when one is present, otherwise from `GET /products?limit=4&sortBy=newest`. That request sends the session store id as `X-Store-ID` because the merchant access token carries a user id, not a store id. The preview does not send a Shopify Admin token. Idle, running, failed, and empty results stay calm copy in the phone. As of dashboard #99, the brand step, the preview step, and Settings do not mount that phone. A missing ready install shows first-build instructions. A ready public https install URL centers the install code. The unmounted component follows the shopper app: opening splash, default home, product, and cart (`components/onboarding/SmartHomePreview.tsx`, copy in `lib/onboarding/shopperChrome.ts`). The home header uses the logo, then the icon, then the name. Splash is not painted as the home header. A blank name uses the shopper Welcome title and does not invent a placeholder. The caption states what the still leaves to the installed app: the installable app shows the published home, or this smart default until Publish, and module-stack edits stay off the device until then. As of 2026-09-29, Brand, Preview, and Settings keep that phone only while the build list has no ready public https install URL, including when the list fails. A loading list does not paint the phone. A ready install replaces it with a compact code and Open Build (`/dashboard/onboarding?step=ready`). Branding editors stay. The device screen does not include Cartaisy product chrome. `/dashboard/app-builder/preview` is a module stack and is labeled that way. It follows the draft section order and says whether that layout is published. It does not call an unpublished draft a live home.
- Home module editor: `app/dashboard/app-builder` provides component management, section ordering/visibility, homescreen preview, and Publish home. The draft is `draftSections` on the dashboard `HomeLayout` document (`PUT /api/home-layout`). Publish writes `sections` and `publishedAt` (`POST /api/home-layout/publish`). Unpublish (`POST /api/home-layout/unpublish`) clears that live snapshot and keeps `draftSections`. A draft save does not replace `sections`. A non-empty `sections` list saved before `publishedAt` existed stays published, and the first load or save sets `publishedAt` from `updatedAt` without clearing `sections`. `GET /api/public/home-feed` returns that `sections` list, and returns an empty layout when `sections` is empty and nothing is published, including after Unpublish while the draft remains. Opening App Builder does not insert a document. Component models include carousel, promo banners, callout banners, category grid, collection displays, collection showcases, category collection grid, and home layout ordering. The installed app reads backend `GET /customer/homescreen`. As of cartaisy-backend #199, that route serves `HomeLayout.sections` only when the layout is live. An unpublished store gets empty module arrays and `layout: []`, and the installable app shows its smart default. Drafts stay in `draftSections`. A non-empty `sections` list with no `publishedAt` stays live.
- Shopify collection/product picker: collection selection exists through `components/app-builder/CollectionSelector.tsx`, which calls `/api/shopify/collections`. That route proxies to backend `GET /api/v1/shopify/collections` and does not read a dashboard access token. Numeric collection ids are kept when the backend returns a Shopify GID. A `shopify_reconnect_required` or Shopify billing code on that response is a catalog block with Reconnect Shopify, not an empty picker. Product picker support was not identified.
- Build/release/status: the onboarding ready step (`/dashboard/onboarding?step=ready`) is the merchant Build my app screen. `lib/build/client.ts` calls backend `POST`/`GET`/`PATCH /api/v1/build-requests` for the authenticated store through `customInstance`, so an expired access token is refreshed and the request is retried once. It does not send a client `storeId`. Eligibility comes from `GET /api/v1/shopify/sync` (`eligibleForBuild`), not from `shopify.lastSyncAt`. The same screen shows a soft strip for the app display name, icon, and splash. As of 2026-09-29, when `GET /api/home-layout` on that screen is Not published yet or Draft, a second quiet strip shows that status and links to `/dashboard/app-builder#publish-home`. Published, and a failed or unrecognized read, leave that strip off. The strip does not change build eligibility, install codes, or Submit. Settings → Build setup does not render this panel. A non-empty trimmed name from the branding draft is shown as itself. When that screen loads branding itself, the name is branding `appName`, then the store name the phone already uses. A missing, blank, or whitespace-only name uses calm copy and links to Brand and Settings Store Branding. The strip does not invent a name and does not fall back to Cartaisy, the shop domain, or a store id. Icon and splash thumbs are https only. Missing assets use those same links. Neither a missing name nor a missing asset changes eligibility. Try again on that screen also reloads the wizard's Shopify connection snapshot. The screen polls one request until each requested platform is ready or failed, and refreshes that request when the tab becomes visible again. While a platform is queued, building, or waiting, the merchant sees a progress card: a three-step rail for queued, building, and ready, or calm failure copy that does not name the build tooling. It does not start EAS or call the platform-admin status route. A request that stays queued keeps that poll, so an install link pasted on the ops queue still appears here once that platform is ready. When a platform is ready and `installUrl` is a non-empty https string, the screen shows Install Android build or Install iOS build. That link opens the backend URL in a new tab with `rel="noopener noreferrer"`. A ready platform without a safe https `installUrl` keeps the Ready label and does not render a button. The screen does not invent a URL. As of 2026-09-29, a ready public https URL is also drawn as a QR in the browser (`qrcode`) above the platform cards, with the URL as text and Copy link. The SVG encodes only that URL. Building, missing, credentialed, and token-shaped values are not encoded. While a platform is queued, building, ready without that public URL, or still unrecognized, the same row keeps a frame the size of the code and says a scannable install code will appear when the preview is ready. It does not draw a code. Failed, not requested, and waiting-on-merchant platforms stay on the progress cards only. The progress rail is unchanged. http, credentialed, and token-shaped values are dropped. Platform ops use `/dashboard/admin/build-requests` (`components/admin/BuildRequestsPanel.tsx`, client in `lib/build/adminClient.ts`) to list every store with `GET /api/v1/admin/build-requests` and to set Android or iOS with `PATCH /api/v1/admin/build-requests/:id/status`. Optional `store.appName`, `store.iconUrl`, and `store.splashUrl` on that list are shown as an icon thumb and a splash thumb. Copy is offered only for a public https URL: splash as `SPLASH_IMAGE_URL=…`, and the icon as `ICON_IMAGE_URL=…` when present. A non-empty trimmed `store.appName` copies as `APP_NAME=…` with no extra quotes. A valid 24-character hex `store.id` copies as `EXPO_PUBLIC_STORE_ID=<id>` with no quotes. The control is labeled `EXPO_PUBLIC_STORE_ID=…` and sits with the app name, icon, and splash controls. The raw id is not the row title. Absent, http, and token-shaped image values stay empty. A missing, blank, or whitespace-only app name stays a calm empty state with no copy control. A missing or invalid store id stays a calm empty state with no copy control. When at least one assignment is copyable, `Copy all EAS env` copies those lines together as `KEY=value` with no quotes and LF newlines, in the order `APP_NAME`, `ICON_IMAGE_URL`, `SPLASH_IMAGE_URL`, `EXPO_PUBLIC_STORE_ID`, skipping any line whose single-copy control is absent. If none qualify, that control is absent. The four single-field controls stay. That block matches the handoff in Cartaisy `docs/MOBILE_MERCHANT_PROVISIONING_RUNBOOK.md`. The status PATCH body may include `installUrl` on that platform (`null` clears it; omitting it leaves the stored link unchanged). Ops can paste an https link on `expo.dev` or `expo.io`, including subdomains such as `u.expo.dev`. The queue shows the current link and can clear it. Other hosts are not sent. The page does not invent URLs, a display name, or a store id (no Cartaisy, shop domain, app name, or build-request id fallback) and does not start EAS. The sidebar link is shown only after that list call succeeds. A 403 clears the queue and shows a platform-ops empty state. Store-owner `super_admin` is not enough. The dashboard does not read `PLATFORM_OPS_EMAILS` or `isPlatformOperator`. A homescreen preview also exists at `app/dashboard/app-builder/preview`. Build my app and Settings → Build setup (`#build-setup`) also connect the store's own App Store Connect API key and Google Play service account through `lib/storeCredentials/client.ts` (`GET`/`POST`/`DELETE /api/v1/store-credentials`). Uploads are multipart (Apple `privateKey` .p8 plus key id and issuer id; Google `serviceAccount` JSON). Responses keep only safe metadata. The private key is not rendered, logged, or sent again after save. Those credentials do not change build eligibility or install links. The dashboard does not call `GET /api/v1/admin/store-credentials/:storeId`. When a requested platform is ready and that platform's credential status is `connected`, Build my app and Settings → Build setup start `POST /api/v1/build-requests/:id/submits` with `{ "platform": "ios" | "android" }` and poll `GET /api/v1/build-requests/:id/submits` and `GET .../submits/:platform` while the status is `queued` or `submitting` (`lib/storeSubmit/client.ts`). The store is the authenticated store. A platform that is not `ready` disables only that submit control. A `ready` platform with a missing or needs-attention credential shows Connect Apple Developer or Connect Google Play and links to the existing store-account card (`#apple-store-account` or `#google-store-account`) instead of a disabled submit button. Preview, Build my app, and install links stay available. A `submitted` job is a confirmation on that platform card: what was sent, that App Store Connect or Play Console may still need review, where to look, and a plain review-time note. It does not add a store URL. Android copy names the Play internal testing track. `failed` shows the safe message and Submit again. `queued` and `submitting` stay a quiet status. Connected Home reads `GET /api/v1/build-requests/:id/submits` for the focused build request and shows those notes on the Go live submit step when a job exists. It does not start a submit. `SUBMIT_ALREADY_IN_PROGRESS` keeps the in-flight job and polls it. Response bodies are not logged. The private key, service-account JSON, and Expo token are not rendered. The contract is cartaisy-backend `docs/cartaisy/STORE_SUBMIT_API.md`.

## Target state:

- Dashboard should act as the merchant/admin UI while backend APIs enforce tenant-safe store ownership, Shopify API access, module reference validation, and publishing rules.
- Dashboard should keep server-only credentials and Shopify Admin/private credentials out of frontend code.
- Dashboard should use clear module contracts for home configuration so backend validation and mobile rendering stay compatible.
- Dashboard architecture docs should be updated when auth, tenancy, Shopify, app-builder, or release handoff behavior changes.

## Known gaps:

- Do not assume any feature or behavior described above is implemented unless verified in the current code.
- The current repo includes local dashboard API routes and Mongoose models for store/module behavior; whether each route should remain dashboard-owned or move behind backend APIs needs product/security review.
- Shopify collection reads now use the backend store token. Explicit backend validation of store-owned Shopify references on home-module publish must still be verified before relying on it. Historical dashboard token documents are not migrated.
- Product picker behavior was not found during the audit.
- Build/release/status handoff: the ready step submits a tracked request, shows live Android and iOS status, and can send a finished platform to App Store Connect or Google Play when that store's account is connected. The client does not choose a Play track. Android uses the backend's internal testing track. The homescreen page at `app/dashboard/app-builder/preview` is a module stack, not the shopper phone. Settings no longer renders the older admin sync-status card. Catalog recovery on that page uses `GET`/`POST /api/v1/shopify/sync`.
- The settings page Shopify card still uses dashboard `/api/shopify/*` routes, which can store an access token. The new onboarding wizard does not call those routes.
- `API_STRUCTURE.md` and `DEVELOPER_GUIDE.md` appear partly stale because they refer to older NextAuth/file names and do not reflect all current app-builder routes.
- Branding: `StoreBrandingColors`, `StoreLogoUpload`, and `StoreAppBrand` each fetch `/admin/stores/:storeId/branding` independently rather than sharing one request — a known, disclosed redundant-GET tradeoff, not yet consolidated. The backend `PATCH` on that endpoint only ever sets a color (a falsy/empty value is ignored, never treated as "clear to null"), so there is deliberately no clear-color affordance in the dashboard UI.
