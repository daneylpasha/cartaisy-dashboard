# Dashboard Status

Last updated: 2026-09-29.

This file is a human/agent-maintained snapshot, not an automatically guaranteed source of truth. Verify code before implementation work.

## Current state:

- Complete enough to identify: Next.js dashboard shell, protected dashboard routes, invite-token signup, store creation on signup, store settings pages, Shopify connect/status/disconnect UI, Shopify collection fetch route, home module CRUD areas, home layout ordering/visibility, homescreen preview, team/settings/orders/customers/analytics/admin surfaces, npm package metadata, local API testing script, GitHub issue templates, a repo-level PR template, and lint/typecheck CI on pull requests.
- Partial: merchant onboarding, store setup/status, Shopify configuration, branding/theme setup, collection selection, backend API compatibility, and role-based admin permissions. These areas exist but need security and product-scope verification before being treated as production-ready SaaS workflows. As of 2026-09-23, invite signup is followed by a guided wizard at `/dashboard/onboarding` (connect, brand, preview, ready for build). The wizard does not write Shopify access tokens. Live Shopify redirect is on (`liveRedirectEnabled: true`) and uses the backend authorize URL. The merchant returns only if `SHOPIFY_OAUTH_RETURN_URL` points at the wizard. The ready step submits a tracked Android/iOS build request and polls status (dashboard #17). It does not start an EAS build. As of 2026-09-24, login and an already-signed-in visit to `/login` or `/signup` send a store with no Shopify connection to that wizard. The signal is `GET /api/v1/shopify/status`, parsed with the wizard's `normalizeConnectionStatus`. Unknown status stays on Home. There is still no persisted "onboarding complete" flag, so a connected store is treated as established and is not redirected. As of 2026-09-28, the cookie banner is deferred on `/dashboard/onboarding` and nested wizard paths so it does not cover the phone or the Brand card. Consent is not stored by that hide. The banner returns on other routes, and Cookie Settings stays on the marketing footer and `/cookies`.
- Invite signup and login can offer Continue with Google when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set. Signup still requires a valid invite token. The Google account email must match the invite and be verified. The dashboard user is stored with `authProvider: 'google'`, `googleSub`, and a random password that the User pre-save hook bcrypt-hashes so it cannot be used to sign in. After create, the browser signs in with backend `POST /auth/google`. The button is hidden when the client id is unset. `.env.example` documents that variable only; it is not a full environment catalog.
- As of 2026-09-28, login links to `/forgot-password`, and `/reset-password` accepts the email link from backend `POST /api/v1/auth/forgot-password` and `POST /api/v1/auth/reset-password` (cartaisy-backend #188 / PR #190). The forgot form always shows the same success copy. A valid reset stores the returned access and refresh tokens the same way as login and opens `/dashboard`. A missing or malformed token shows an invalid-link state with links back to forgot password and sign in. Continue with Google stays on the login page. The reset token and the new password are not shown in the page, the address bar after submit, or logs.
- Not started or not identified in audited files: product picker workflow, release publishing beyond a finished-build submit, a complete environment catalog, and a full automated test suite. `npm run test:auth-google` covers the invite Google signup decision (email mismatch, unverified email, success) with a mocked verifier. `npm run test:auth-password-reset` covers reset-token shape and that public reset copy does not include a token or password.

## Target state:

- Merchant onboarding should guide a store owner from invitation through store setup readiness: account, store, Shopify connection, branding, home modules, preview, and any build/release handoff.
- Store setup/status should give merchants and admins a reliable readiness view.
- Shopify connection/configuration should be tenant-safe and backend-mediated.
- Branding/theme setup should document and validate every field consumed by mobile apps.
- Home module editor should publish only valid, store-owned Shopify references and maintain compatibility with backend/mobile contracts.
- Testing/CI and release readiness should be explicit enough for small PRs and human review.

- Testing/CI: lint and typecheck now exist and run automatically. `npm run lint` (ESLint 9 flat config via `eslint-config-next`) and `npm run type-check` (`tsc --noEmit`) are defined in `package.json`, and `.github/workflows/ci.yml` runs both plus `npm run test:auth-google` on every pull request against `main` using Node 20. Two caveats. First, there is still no general automated test suite — no unit, integration, or e2e runner — so CI proves the code lints, type-checks, and the invite Google signup decision, not that the rest of the app works; `npm run test:api` remains a manual script against a live server. Second, the lint baseline is not clean: linting a previously unlinted repo surfaced 176 pre-existing violations — `@typescript-eslint/no-explicit-any` (136), `react/no-unescaped-entities` (34), `@typescript-eslint/no-empty-object-type` (6). Those rules keep their real `error` severity; the existing violations are recorded per file and per rule in `eslint-suppressions.json` (ESLint's bulk-suppressions mechanism) rather than being fixed. Because entries are per file and per rule, the baseline guarantees the debt cannot grow: a violation in an unrecorded file, a count above the recorded one, or a fix in one file paired with a new violation in another all fail CI. The known residual gap is that a violation can be swapped for another *within the same file for the same rule*, since entries record counts rather than identities — closing that would need per-violation tracking ESLint does not provide, or fixing all 176. The `react-hooks/rules-of-hooks` violation that same baseline surfaced in `app/dashboard/app-builder/page.tsx` was suppressed at the time and has since been fixed (see the App Builder gap below), so no `react-hooks/rules-of-hooks` suppression remains. Unrelated pre-existing `eslint-disable` comments elsewhere (an `exhaustive-deps` one in `components/Sidebar.tsx`, an unused-vars one in `lib/auth/server.ts`, and `no-redeclare` ones throughout the generated Orval client) were not part of that baseline and are untouched. The demoted-rule warnings are known debt to burn down, not an endorsement.
- App Builder: `SortableItem` in `app/dashboard/app-builder/page.tsx` called `useSortable()` after an early `return null` guard on a `componentConfig` lookup, so the hook was skipped whenever a section's `type` was not one of that file's hardcoded config keys. Fixed 2026-07-28 by hoisting the hook above the guard, which also removed the `eslint-disable react-hooks/rules-of-hooks` block left behind by the lint-baseline work. The observed effect of the bug: when a section became unmapped, the row kept a stale registration in `DndContext` under its previous id while rendering nothing, so drag-and-drop still treated an invisible row as an occupied sortable slot. Worth recording accurately for anyone reading the original suppression comment — React did *not* throw "Rendered fewer hooks than expected" for this shape, because that check only fires when at least one hook was consumed, and a guard placed before every hook goes undetected. The defect was real but silent, not a crash. The root cause behind that bug was closed on 2026-07-28: the page previously redeclared its own `LayoutSection` interface with `type: string` and typed `componentConfig` as `Record<string, …>`, so nothing stopped the two from drifting. It now reuses `IHomeLayoutSection` from `models/HomeLayout.ts` — the type that already governs this page's actual data path via `/api/home-layout` and `lib/services/homeLayout` — and keys `componentConfig` as `Record<IHomeLayoutSection['type'], …>`. Adding a section type to the model without adding its config entry, or removing one while the config still lists it, is now a `npm run type-check` failure rather than a silent runtime `undefined`; both directions were verified by temporarily editing the union and observing TS2741 and TS2353. The import is deliberately `import type`, because `models/HomeLayout.ts` instantiates a Mongoose model at module scope and a value import from this client component would pull mongoose into the browser bundle. The runtime `if (!config) return null` guard is retained on purpose — TypeScript does not constrain what is already stored in MongoDB. The generated `LayoutSectionResponseType` in `lib/api/generated/` was deliberately not used; this page reads the dashboard's own Mongoose model, and moving it onto the generated backend client is separate Phase 4 work.
