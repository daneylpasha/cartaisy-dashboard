# Dashboard Status

Last updated: 2026-09-23.

This file is a human/agent-maintained snapshot, not an automatically guaranteed source of truth. Verify code before implementation work.

## Current state:

- Complete enough to identify: Next.js dashboard shell, protected dashboard routes, invite-token signup, store creation on signup, store settings pages, Shopify connect/status/disconnect UI, Shopify collection fetch route, home module CRUD areas, home layout ordering/visibility, homescreen preview, team/settings/orders/customers/analytics/admin surfaces, npm package metadata, local API testing script, GitHub issue templates, a repo-level PR template, and lint/typecheck CI on pull requests.
- Partial: merchant onboarding, store setup/status, Shopify configuration, branding/theme setup, collection selection, backend API compatibility, and role-based admin permissions. These areas exist but need security and product-scope verification before being treated as production-ready SaaS workflows.
- Not started or not identified in audited files: product picker workflow, dedicated app build request workflow, app-store submission workflow, release status handoff, repo-level env examples, and full automated test suite.

## Target state:

- Merchant onboarding should guide a store owner from invitation through store setup readiness: account, store, Shopify connection, branding, home modules, preview, and any build/release handoff.
- Store setup/status should give merchants and admins a reliable readiness view.
- Shopify connection/configuration should be tenant-safe and backend-mediated.
- Branding/theme setup should document and validate every field consumed by mobile apps.
- Home module editor should publish only valid, store-owned Shopify references and maintain compatibility with backend/mobile contracts.
- Testing/CI and release readiness should be explicit enough for small PRs and human review.

## Known gaps:

- Do not assume any feature or behavior described above is implemented unless verified in the current code.
- Merchant onboarding: current signup is invite-token based, but a full guided readiness checklist was not found.
- Store setup/status: dashboard home has status-style cards, but no canonical setup readiness model was identified.
- Shopify connection/configuration (2026-09-23, issue #15): new connects call the backend only. `POST /api/v1/shopify/oauth/connect`, `GET /api/v1/shopify/status`, `POST /api/v1/shopify/disconnect`, and `POST /api/v1/shopify/sync` are the dashboard contract from cartaisy-backend #153 / PR #157. The settings card shows the connected shop domain read-only, and Reconnect restarts that same connect call. Sync again calls `POST /api/v1/shopify/sync`. Dashboard routes `app/api/shopify/connect`, `callback`, `status`, and `disconnect`, plus `app/api/v1/shopify/oauth/callback`, no longer exchange a code or write `shopify.accessToken`. `models/Store.ts` has no access token path, so a dashboard Mongoose write of that field is dropped. Collections are proxied to `GET /api/v1/shopify/collections` and no longer read a dashboard token. Remaining gaps: historical tokens already stored in the dashboard database are not migrated or deleted; a store that was connected only in that database shows as disconnected until the merchant reconnects; the backend must be deployed with these routes and `SHOPIFY_OAUTH_RETURN_URL` pointed at the dashboard settings page (later, the onboarding step from #16) or the browser will not return to this UI; durable sync status is still the older sync-status endpoint and backend #154. Issue #16 (onboarding wizard) had no open pull request when this landed. The shared client is `lib/api/shopifyConnection.ts` and `components/shopify/ConnectShopify.tsx`.
- Branding/theme setup: logo upload exists. Primary/secondary color editing was added (`components/settings/StoreBrandingColors.tsx`, wired into `app/dashboard/settings/page.tsx`'s Store Branding section), consuming the existing, already-validated `GET`/`PATCH /admin/stores/:storeId/branding` endpoint with no backend changes. Verified manually via a headless-browser pass — no automated test suite exists in this repo to add coverage to (see the Testing/CI gap below) — covering: default-color rendering when a store has no `primaryColor`/`secondaryColor` set; an invalid hex value blocks Save without corrupting the last-committed color; a valid change enables the otherwise-disabled Save button; a save attempted without a valid store context surfaces an error rather than failing silently. Known gaps, not yet resolved: no automated test coverage; `StoreBrandingColors` fetches branding independently of `StoreLogoUpload` rather than through shared state (one redundant `GET` per page load); the backend `PATCH` only ever sets a color and never clears one to `null`, so there is no "clear color" affordance; any broader "theme" fields beyond primary/secondary color were not audited as part of this work.
- Home module editor: module types exist, but draft/publish/status semantics and backend/mobile contract enforcement need verification.
- Collection/product picker: collection selector exists; product picker was not identified.
- Preview/build handoff: homescreen preview exists; build/release handoff was not identified.
- Auth/store ownership: route-level store scoping exists in many places; cross-route consistency should be audited before high-risk changes.
- API compatibility with backend: Orval config and direct backend calls exist; generated client freshness and backend API compatibility must be verified.
- Testing/CI: lint and typecheck now exist and run automatically. `npm run lint` (ESLint 9 flat config via `eslint-config-next`) and `npm run type-check` (`tsc --noEmit`) are defined in `package.json`, and `.github/workflows/ci.yml` runs both on every pull request against `main` using Node 20. Two caveats. First, there is still no automated test suite — no unit, integration, or e2e runner — so CI proves the code lints and type-checks, not that it works; `npm run test:api` remains a manual script against a live server. Second, the lint baseline is not clean: linting a previously unlinted repo surfaced 176 pre-existing violations — `@typescript-eslint/no-explicit-any` (136), `react/no-unescaped-entities` (34), `@typescript-eslint/no-empty-object-type` (6). Those rules keep their real `error` severity; the existing violations are recorded per file and per rule in `eslint-suppressions.json` (ESLint's bulk-suppressions mechanism) rather than being fixed. Because entries are per file and per rule, the baseline guarantees the debt cannot grow: a violation in an unrecorded file, a count above the recorded one, or a fix in one file paired with a new violation in another all fail CI. The known residual gap is that a violation can be swapped for another *within the same file for the same rule*, since entries record counts rather than identities — closing that would need per-violation tracking ESLint does not provide, or fixing all 176. The `react-hooks/rules-of-hooks` violation that same baseline surfaced in `app/dashboard/app-builder/page.tsx` was suppressed at the time and has since been fixed (see the App Builder gap below), so no `react-hooks/rules-of-hooks` suppression remains. Unrelated pre-existing `eslint-disable` comments elsewhere (an `exhaustive-deps` one in `components/Sidebar.tsx`, an unused-vars one in `lib/auth/server.ts`, and `no-redeclare` ones throughout the generated Orval client) were not part of that baseline and are untouched. The demoted-rule warnings are known debt to burn down, not an endorsement.
- App Builder: `SortableItem` in `app/dashboard/app-builder/page.tsx` called `useSortable()` after an early `return null` guard on a `componentConfig` lookup, so the hook was skipped whenever a section's `type` was not one of that file's hardcoded config keys. Fixed 2026-07-28 by hoisting the hook above the guard, which also removed the `eslint-disable react-hooks/rules-of-hooks` block left behind by the lint-baseline work. The observed effect of the bug: when a section became unmapped, the row kept a stale registration in `DndContext` under its previous id while rendering nothing, so drag-and-drop still treated an invisible row as an occupied sortable slot. Worth recording accurately for anyone reading the original suppression comment — React did *not* throw "Rendered fewer hooks than expected" for this shape, because that check only fires when at least one hook was consumed, and a guard placed before every hook goes undetected. The defect was real but silent, not a crash. The root cause behind that bug was closed on 2026-07-28: the page previously redeclared its own `LayoutSection` interface with `type: string` and typed `componentConfig` as `Record<string, …>`, so nothing stopped the two from drifting. It now reuses `IHomeLayoutSection` from `models/HomeLayout.ts` — the type that already governs this page's actual data path via `/api/home-layout` and `lib/services/homeLayout` — and keys `componentConfig` as `Record<IHomeLayoutSection['type'], …>`. Adding a section type to the model without adding its config entry, or removing one while the config still lists it, is now a `npm run type-check` failure rather than a silent runtime `undefined`; both directions were verified by temporarily editing the union and observing TS2741 and TS2353. The import is deliberately `import type`, because `models/HomeLayout.ts` instantiates a Mongoose model at module scope and a value import from this client component would pull mongoose into the browser bundle. The runtime `if (!config) return null` guard is retained on purpose — TypeScript does not constrain what is already stored in MongoDB. The generated `LayoutSectionResponseType` in `lib/api/generated/` was deliberately not used; this page reads the dashboard's own Mongoose model, and moving it onto the generated backend client is separate Phase 4 work.
- Release readiness: no dedicated release checklist existed before this document.
