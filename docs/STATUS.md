# Dashboard Status

Last updated: 2026-09-24.

This file is a human/agent-maintained snapshot, not an automatically guaranteed source of truth. Verify code before implementation work.

## Current state:

- Complete enough to identify: Next.js dashboard shell, protected dashboard routes, invite-token signup, store creation on signup, store settings pages, Shopify connect/status/disconnect UI, Shopify collection fetch route, home module CRUD areas, home layout ordering/visibility, homescreen preview, team/settings/orders/customers/analytics/admin surfaces, npm package metadata, local API testing script, GitHub issue templates, a repo-level PR template, and lint/typecheck CI on pull requests.
- Partial: merchant onboarding, store setup/status, Shopify configuration, branding/theme setup, collection selection, backend API compatibility, and role-based admin permissions. These areas exist but need security and product-scope verification before being treated as production-ready SaaS workflows. As of 2026-09-23, invite signup is followed by a guided wizard at `/dashboard/onboarding` (connect, brand, preview, ready for build). The wizard does not write Shopify access tokens. Live Shopify redirect is on (`liveRedirectEnabled: true`) and uses the backend authorize URL. The merchant returns only if `SHOPIFY_OAUTH_RETURN_URL` points at the wizard. The ready step submits a tracked Android/iOS build request and polls status (dashboard #17). It does not start an EAS build. As of 2026-09-24, login and an already-signed-in visit to `/login` or `/signup` send a store with no Shopify connection to that wizard. The signal is `GET /api/v1/shopify/status`, parsed with the wizard's `normalizeConnectionStatus`. Unknown status stays on Home. There is still no persisted "onboarding complete" flag, so a connected store is treated as established and is not redirected.
- Invite signup and login can offer Continue with Google when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set. Signup still requires a valid invite token. The Google account email must match the invite and be verified. The dashboard user is stored with `authProvider: 'google'`, `googleSub`, and a random password that the User pre-save hook bcrypt-hashes so it cannot be used to sign in. After create, the browser signs in with backend `POST /auth/google`. The button is hidden when the client id is unset. `.env.example` documents that variable only; it is not a full environment catalog.
- Not started or not identified in audited files: product picker workflow, app-store submission workflow, release status handoff beyond the tracked build request, a complete environment catalog, and a full automated test suite. `npm run test:auth-google` covers the invite Google signup decision (email mismatch, unverified email, success) with a mocked verifier.

## Target state:

- Merchant onboarding should guide a store owner from invitation through store setup readiness: account, store, Shopify connection, branding, home modules, preview, and any build/release handoff.
- Store setup/status should give merchants and admins a reliable readiness view.
- Shopify connection/configuration should be tenant-safe and backend-mediated.
- Branding/theme setup should document and validate every field consumed by mobile apps.
- Home module editor should publish only valid, store-owned Shopify references and maintain compatibility with backend/mobile contracts.
- Testing/CI and release readiness should be explicit enough for small PRs and human review.

## Known gaps:

- Do not assume any feature or behavior described above is implemented unless verified in the current code.
- Merchant onboarding: invite signup still creates the account. New accounts are sent to `/dashboard/onboarding`. Login is also continued into that wizard when Shopify is not connected (see the 2026-09-24 routing note above). The wizard can be completed through preview without ops help. Connect calls backend Shopify routes only and does not write a dashboard access token. With `liveRedirectEnabled` true, the primary action opens Shopify. A return of `shopify=connected` shows the success copy, catalog sync progress, and the product count once the overview has it (or "Not synced yet"). Idle or failed sync is started once with `POST /api/v1/shopify/sync`; a 409 does not start a second run. Continue to Brand stays available. A return of `shopify=error` shows `shopifyReturnCopy` for the backend reason, with Try again. Those query params are removed after they are read. Splash and app icon can be chosen for the preview; the current branding API persists logo and colors only. App name is the dashboard store name. The wizard shell is dashboard #16 / PR #18; #15 only turns on the live connect return. Post-connect sync on that step is dashboard #25.
- Store setup/status: there is still no persisted setup-readiness record. As of 2026-09-24, Home (`app/dashboard/page.tsx`) no longer renders a generic template or a hardcoded "Active" app status. A store that is not Shopify-connected sees a four-step checklist (Connect, Branding, Preview, Build my app) that links into the existing wizard. A connected store shows catalog sync from `GET /api/v1/shopify/sync`, build status from `GET /api/v1/build-requests`, and counts only when those APIs return them. `shopify.lastSyncAt` is not treated as a successful sync. Preview completion is not stored, so it is never shown as done. The shell (sidebar and top bar) uses the same connection status: Connect Shopify stays visible until the store is connected, and orders, customers, collections, the app builder, and similar links sit behind an "After you connect" disclosure until then. Those routes remain reachable, including from the disclosure and by URL.
- Shopify connection/configuration (2026-09-23, issue #15): new connects call the backend only, from settings and from the onboarding wizard. `POST /api/v1/shopify/oauth/connect`, `GET /api/v1/shopify/status`, `POST /api/v1/shopify/disconnect`, and `POST /api/v1/shopify/sync` are the dashboard contract from cartaisy-backend #153 / PR #157, which is merged. The settings card shows the connected shop domain read-only, and Reconnect restarts that same connect call. Sync again calls `POST /api/v1/shopify/sync`. The wizard keeps its own client in `lib/onboarding/shopifyConnect.ts` with `liveRedirectEnabled: true`. The backend ignores a client `returnTo` and redirects to `SHOPIFY_OAUTH_RETURN_URL`. Dashboard routes `app/api/shopify/connect`, `callback`, `status`, and `disconnect`, plus `app/api/v1/shopify/oauth/callback`, no longer exchange a code or write `shopify.accessToken`. `models/Store.ts` has no access token path, so a dashboard Mongoose write of that field is dropped. Collections are proxied to `GET /api/v1/shopify/collections` and no longer read a dashboard token. Remaining gaps: historical tokens already stored in the dashboard database are not migrated or deleted; a store that was connected only in that database shows as disconnected until the merchant reconnects; `SHOPIFY_OAUTH_RETURN_URL` must point at `/dashboard/onboarding?step=connect` or the browser will not return to the wizard. The onboarding wizard and the build screen read durable catalog sync from `GET /api/v1/shopify/sync` (backend #154 / PR #158). `shopify.lastSyncAt` is not treated as a successful sync. The settings sync card still uses the older admin sync-status endpoint and is not the build gate. Overlap with PR #18 is limited to the connect flag, the return-query message, and shared docs. The wizard shell is unchanged.
- Branding/theme setup: logo upload exists. Primary/secondary color editing was added (`components/settings/StoreBrandingColors.tsx`, wired into `app/dashboard/settings/page.tsx`'s Store Branding section), consuming the existing, already-validated `GET`/`PATCH /admin/stores/:storeId/branding` endpoint with no backend changes. Verified manually via a headless-browser pass — no automated test suite exists in this repo to add coverage to (see the Testing/CI gap below) — covering: default-color rendering when a store has no `primaryColor`/`secondaryColor` set; an invalid hex value blocks Save without corrupting the last-committed color; a valid change enables the otherwise-disabled Save button; a save attempted without a valid store context surfaces an error rather than failing silently. Known gaps, not yet resolved: no automated test coverage; `StoreBrandingColors` fetches branding independently of `StoreLogoUpload` rather than through shared state (one redundant `GET` per page load); the backend `PATCH` only ever sets a color and never clears one to `null`, so there is no "clear color" affordance; any broader "theme" fields beyond primary/secondary color were not audited as part of this work.
- Home module editor: module types exist, but draft/publish/status semantics and backend/mobile contract enforcement need verification.
- Collection/product picker: collection selector exists; product picker was not identified.
- Preview/build handoff: the brand step and the preview step share a smart-default home that follows the branding draft in the same render (app name, colors, logo, icon, and splash; no save or reload). The device screen has no Cartaisy wordmark, logo, or marketing chrome. The wizard header outside the phone still says Cartaisy. The home shows the app name, colors, logo/icon/splash when present, up to four synced products with title, image, and price when catalog sync succeeded, and read-only collection names when the backend returns them. Idle, running, failed, or empty catalogs show calm copy in the phone instead of placeholder tiles. It does not require the home module editor. The ready step is the Build my app screen (`components/onboarding/BuildMyAppPanel.tsx`, client in `lib/build/client.ts`). It submits `POST /api/v1/build-requests` for Android, iOS, or both, with an optional access note of at most 280 characters, then polls `GET /api/v1/build-requests/:id` every few seconds while a requested platform is `queued`, `building`, or `waiting_on_merchant`. Polling stops when every requested platform is `ready` or `failed`. Submit stays off unless `GET /api/v1/shopify/sync` reports `eligibleForBuild` and Shopify is connected. A 409 `BUILD_NOT_ELIGIBLE` with `shopify_not_connected` offers Connect Shopify; `catalog_sync_not_succeeded` offers Sync again. `waiting_on_merchant` is labeled Waiting on Apple for iOS and Waiting on you for Android. Try again refreshes the Shopify connection snapshot after the build list loads, so a failed `GET /shopify/status` does not keep the merchant blocked. Build requests go through `customInstance`: an expired access token is refreshed and retried once, and a 401 that survives that refresh tells the merchant to sign in instead of polling silently. The screen does not start EAS, show build logs, or render request ids. The app-builder homescreen preview is unchanged. App-store submission is still not implemented. The contract is cartaisy-backend `docs/cartaisy/BUILD_REQUEST_API.md` (PR #159). As of 2026-09-24, Cartaisy operators can open `/dashboard/admin/build-requests` to see those requests across stores (name, shop domain, platforms, access note, timestamps) and set Android and iOS status independently. The page polls the list. The link stays hidden unless `GET /api/v1/admin/build-requests` succeeds. A store owner, including `super_admin`, gets a 403 empty state and no other store's notes. Access is `User.isPlatformOperator` or a verified email in backend `PLATFORM_OPS_EMAILS` (backend #170 / PR #168). The dashboard does not grant that access.
- Auth/store ownership: route-level store scoping exists in many places; cross-route consistency should be audited before high-risk changes.
- API compatibility with backend: Orval config and direct backend calls exist; generated client freshness and backend API compatibility must be verified.
- Testing/CI: lint and typecheck now exist and run automatically. `npm run lint` (ESLint 9 flat config via `eslint-config-next`) and `npm run type-check` (`tsc --noEmit`) are defined in `package.json`, and `.github/workflows/ci.yml` runs both plus `npm run test:auth-google` on every pull request against `main` using Node 20. Two caveats. First, there is still no general automated test suite — no unit, integration, or e2e runner — so CI proves the code lints, type-checks, and the invite Google signup decision, not that the rest of the app works; `npm run test:api` remains a manual script against a live server. Second, the lint baseline is not clean: linting a previously unlinted repo surfaced 176 pre-existing violations — `@typescript-eslint/no-explicit-any` (136), `react/no-unescaped-entities` (34), `@typescript-eslint/no-empty-object-type` (6). Those rules keep their real `error` severity; the existing violations are recorded per file and per rule in `eslint-suppressions.json` (ESLint's bulk-suppressions mechanism) rather than being fixed. Because entries are per file and per rule, the baseline guarantees the debt cannot grow: a violation in an unrecorded file, a count above the recorded one, or a fix in one file paired with a new violation in another all fail CI. The known residual gap is that a violation can be swapped for another *within the same file for the same rule*, since entries record counts rather than identities — closing that would need per-violation tracking ESLint does not provide, or fixing all 176. The `react-hooks/rules-of-hooks` violation that same baseline surfaced in `app/dashboard/app-builder/page.tsx` was suppressed at the time and has since been fixed (see the App Builder gap below), so no `react-hooks/rules-of-hooks` suppression remains. Unrelated pre-existing `eslint-disable` comments elsewhere (an `exhaustive-deps` one in `components/Sidebar.tsx`, an unused-vars one in `lib/auth/server.ts`, and `no-redeclare` ones throughout the generated Orval client) were not part of that baseline and are untouched. The demoted-rule warnings are known debt to burn down, not an endorsement.
- App Builder: `SortableItem` in `app/dashboard/app-builder/page.tsx` called `useSortable()` after an early `return null` guard on a `componentConfig` lookup, so the hook was skipped whenever a section's `type` was not one of that file's hardcoded config keys. Fixed 2026-07-28 by hoisting the hook above the guard, which also removed the `eslint-disable react-hooks/rules-of-hooks` block left behind by the lint-baseline work. The observed effect of the bug: when a section became unmapped, the row kept a stale registration in `DndContext` under its previous id while rendering nothing, so drag-and-drop still treated an invisible row as an occupied sortable slot. Worth recording accurately for anyone reading the original suppression comment — React did *not* throw "Rendered fewer hooks than expected" for this shape, because that check only fires when at least one hook was consumed, and a guard placed before every hook goes undetected. The defect was real but silent, not a crash. The root cause behind that bug was closed on 2026-07-28: the page previously redeclared its own `LayoutSection` interface with `type: string` and typed `componentConfig` as `Record<string, …>`, so nothing stopped the two from drifting. It now reuses `IHomeLayoutSection` from `models/HomeLayout.ts` — the type that already governs this page's actual data path via `/api/home-layout` and `lib/services/homeLayout` — and keys `componentConfig` as `Record<IHomeLayoutSection['type'], …>`. Adding a section type to the model without adding its config entry, or removing one while the config still lists it, is now a `npm run type-check` failure rather than a silent runtime `undefined`; both directions were verified by temporarily editing the union and observing TS2741 and TS2353. The import is deliberately `import type`, because `models/HomeLayout.ts` instantiates a Mongoose model at module scope and a value import from this client component would pull mongoose into the browser bundle. The runtime `if (!config) return null` guard is retained on purpose — TypeScript does not constrain what is already stored in MongoDB. The generated `LayoutSectionResponseType` in `lib/api/generated/` was deliberately not used; this page reads the dashboard's own Mongoose model, and moving it onto the generated backend client is separate Phase 4 work.
